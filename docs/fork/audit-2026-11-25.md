# Fork audit — 2026-11-25

A second whole-fork review, eight days after [audit-2026-11-17.md](audit-2026-11-17.md).
The base is upstream `main` at `a0729fa5`, which is also the merge base: the
fork is 0 commits behind. On top of it sit 122 fork commits and 35 merges, 16
of them from upstream: about 80 k added and 29 k removed lines in 502 files,
`ggml/` included. The review weighted the changes since `a13f2f45` (the
previous audit) and the code that audit did not read line by line. That code
is the model ports, the shared loader and backend helpers, the plugin loader's
non-Windows path, the build system, the bindings' documentation, and the
upstream phrase-boost merge.

## Method

1. **Transcript A/B against today's upstream.** Upstream `a0729fa5` was built
   in a scratch worktree with the fork's CPU flags (`GGML_NATIVE=ON`,
   `GGML_OPENMP=OFF`, `GGML_CPU_REPACK=ON`, static). Both CLIs ran 21 local
   models over 11 clips each, as one `--batch` session per model on the CPU
   backend. The clips were English, French, German, Japanese, Chinese,
   Russian, silence-heavy, product names and 35 s of speech. Every
   difference was then attributed with single-clip runs, kill switches and
   tensor dumps. Streaming: Nemotron 3.5 and Moonshine streaming at 160 ms
   chunks on 5 clips, with the fork run with and without the silence fast
   path (`TRANSCRIBE_DISABLE_ACTIVITY_GATE=1`).
2. **Static analysis.** `clang-tidy` (NDK 30, LLVM) ran over the 68
   fork-changed C/C++ files, compiled as Android arm64, so the non-Windows
   code paths were parsed too. Checks: the clang analyzer's core, C++, unix
   and dead-code sets, plus the bug-finding `bugprone-*` and
   `performance-*` checks.
3. **Code reading.** Read in full:
   - the Parakeet decoder's merge of phrase boosting with the GPU decoder and
     the allowlist;
   - every family's allowlist code (Parakeet, Whisper, Granite, SenseVoice,
     R2T2) and the shared code matching;
   - the stream VAD front end, the speech gate and the R2T2 stream;
   - the loader, the backend and threadpool helpers;
   - the plugin loader, the model-set CMake and the Rust `build.rs` cache;
   - the C header and Rust docs for every fork addition.
4. **Gates.** Build, `ctest`, `cargo test`, the Python/TypeScript and Rust
   binding drift gates, `clang-format`, and the teardown lint.

## Differences from upstream, attributed

231 model-clip pairs ran. 22 belong to the two fork-only models, and on 3
both arms stopped Moonshine the same way, which leaves 206 comparable pairs:
179 identical and 27 different. Ten models are byte-identical on every clip:
Canary, Cohere, GigaAM CTC and RNN-T, Granite NAR, Granite 5 CTC, MedASR,
Moonshine, Moonshine streaming and SenseVoice. Every difference has one of
these causes:

- **Upstream's transcripts depend on session history (Granite).** Upstream
  keeps Granite's KV cache across runs and only grows it, so a clip's
  attention window is sized by the longest clip the session ran before. ggml's
  F16 dot products then split differently between SIMD lanes and the scalar
  tail, and a comma can move. The fork releases the cache after every run, so
  each clip gets its own size. Run alone in a fresh session, upstream writes
  the fork's text exactly (`dots`, `fleurs-ja`). Tensor dumps on `fleurs-ja`
  are bit-identical at every stage up to the first decoder step: mel,
  encoder blocks, projector, prefill blocks and logits. That includes the
  fork's direct depthwise convolution. The fork's behaviour is the better
  one: a host that reuses sessions (ZER0's Multi-STT) gets the same
  transcript for the same audio.
- **CPU_REPACK (Parakeet family).** See item 6. With
  `TRANSCRIBE_NO_CPU_REPACK=1` Parakeet's CPU transcripts equal upstream's:
  CTC, Nemotron and Ultra, offline and streaming, were checked byte for byte.
  This also corrects the previous audit, which put the fork's one-comma CPU
  streaming difference down to upstream's older ggml. Upstream now runs the
  same ggml and the comma stays; without the repack it goes.
- **The fork's Qwen3-ASR encoder.** The windowed attention behind R2T2's
  encoder cache replaces upstream #224 by design (FLEURS-fr WER 4.95% vs
  5.44%, [fork sync record](../plans/2026-11-fork-master-plan.md)). Its
  differences are punctuation and names, mostly in the fork's favour
  ("Quirk ... Quattro" vs upstream's "Quark ... Quadro").
- **Fork-only models.** Parakeet Redux (TQ1_G128) and R2T2 do not load
  upstream.

Moonshine's repetition and truncation stops (`german`, `product-names`) occur
identically in both arms. Whisper's one difference is a hallucination on
near-silence (`jobs-silence`): with `seed = 0` its temperature fallback draws
a random seed, and the text changes from run to run in both arms (by design,
`include/transcribe/whisper.h`).

### Streaming

Nemotron, 160 ms chunks: `jfk`, `jobs-silence` and `fleurs-fr` are identical
to upstream. `german` and `dots` differ by punctuation, and with or without
the silence fast path the fork's text is the same. With
`TRANSCRIBE_NO_CPU_REPACK=1` it equals upstream's (checked on `german`).

Moonshine streaming: identical on `jfk`, `jobs-silence` and `german`. On
`fleurs-fr` the silence fast path changes the result. That clip is so quiet
that no 16 ms window reaches -42 dBFS, and the English-only tiny model writes
nothing for it without the fast path (fork and upstream alike). With the fast
path, which removes the leading silence the model would otherwise see, it
hallucinates "A person who is in a relationship with a". Both outputs are
wrong for French speech. It does show that cutting leading silence can change
what a family that keeps committed behind input writes; ZER0 opens every
stream with `enable_vad = false`. Moonshine on `dots` was not compared: that run
was stopped to free the CPU (below).

## CUDA A/B (2026-11-26)

The same 22 local models and 11 clips as the CPU A/B, on the RTX 4070
(`--backend cuda`, batch size 1). Fork arm: `build-cuda` (CUDA graphs on).
Upstream arm: `a0729fa5` built with `TRANSCRIBE_CUDA=ON` and upstream's
defaults (graphs off). Of 242 pairs, 22 belong to the fork-only models, and on
5 both arms stopped the same way (repetition or length cap). That leaves 215:
186 identical, 29 different. Seven models are identical on every clip:
Granite NAR, Granite 5 CTC, MedASR, Moonshine, Moonshine streaming, SenseVoice
and Fun-ASR-Nano (the SAN-M direct conv stays off on GPUs, item 16). Every
difference has one of these causes, each confirmed with a switch that gives
upstream's text exactly:

- **Attention on the GPU (18).** Canary 3, Cohere 2, GigaAM CTC 5, GigaAM
  RNN-T 1, Parakeet CTC 3, v3 2, Ultra 1 and Nemotron 1. Upstream sends the
  attention these models' CUDA kernels cannot take (a per-head rel-pos mask,
  GigaAM's head size 48) to the CPU; the fork's flash probe keeps it on the
  device (1.8-2.45x faster encoders, 2026-11-17). `TRANSCRIBE_FORCE_FLASH=1`
  restores upstream's path and text on all 18.
- **Nemotron `ru-short` (1).** The probe plus the causal `conv0` (item 17).
  With `TRANSCRIBE_FORCE_FLASH=1 TRANSCRIBE_CONV_DIRECT_CONV0=1` all 11
  Nemotron clips and all 21 dumped tensors, the decoder's included, are
  byte-identical to upstream's. That also shows the fork's on-device decoder is
  byte-identical.
- **Granite's direct depthwise conv (3).** Granite 4.0 `fleurs-fr`, `ru-short`
  and 4.1 `ru-short`. It is bit-identical to im2col on the CPU, not on CUDA.
  `TRANSCRIBE_CONV_NO_DIRECT_DW=1` gives upstream's text. Single-clip runs
  were checked, so upstream's session-history effect is not the cause here.
- **The fork's Qwen3-ASR encoder (6).** By design; mostly the same clips as on
  CPU.
- **Whisper on near-silence (1).** With `seed = 0` its fallback draws a random
  seed: six runs gave six outputs, in both arms.

## Checked, no change needed

- **Phrase boost × GPU decoder × allowlist** (`8b1e6759`). At the automaton's
  root `PhraseBoost::apply` adds 0 to every logit: a term's first piece earns
  no bonus, and the root's `locked` and `earned` are 0. So the device's
  masked argmax is already the biased answer there. Inside a match the column
  is fetched and re-ranked on the host by the same `boost_rerank` the CPU
  loop uses. Blank still decides alone, and blocked tags stay unreachable.
  The TDT fast-forward over repeated blank/duration-0 steps is
  iteration-exact.
- **Integrated-GPU decoder rule** (`e5d0af8d`): per session, from the model's
  own device.
- **Speech gate**: a frame is never released twice; a NaN is refused before
  anything is consumed; `finish` releases only the real samples of the padded
  frame.
- **R2T2 stream**: the cursors stay consistent on every error path, finalize
  always runs one full pass, and the silence opt-out is per stream.
- **Allowlist code matching** (`transcribe-lang.h`): a regional request
  never crosses to another primary language, and aliases are folded on both
  sides. An empty `language` never reaches a family: the dispatcher rejects it
  on every model with a language list.
- **Stubs** for families left out of a model set: every family-specific
  entry point has one, with the same defaults as the real initializer.
- **Loader**: TQ1 re-layout, the CPU_REPACK hand-back, and the whole-tensor
  path for dtype conversion. **Backend helpers**: the threadpool map,
  parking, and reclaim-and-retry limited to the caller's own backend.
- **`build.rs` install-tree clearing** (`b34474e6`).
- **Speech.cpp hand-off, item 2** (a non-F32 FSMN kernel reaching
  `ggml_conv_2d_dw_direct` in SANM's batched path): ggml 1.0 runs F16 depthwise
  kernels on CPU, CUDA and Vulkan, and the published SenseVoice GGUF stores
  all 70 FSMN kernels as F32. Not a bug today. The "misbehaves for non-f32
  kernels" casts in the encoders predate ggml 1.0 and are harmless.
- **clang-tidy**: no defect beyond item 10. The one analyzer report
  (`conformer.cpp:938`, a null `pos_proj`) is a false positive: the tensor is
  non-null by construction. The widening-cast reports are all small products.

## Open items

1. **CPU_REPACK.** It stays on: it is the fork's main CPU speed-up for the
   Parakeet family, and its WER effect is nil (above).

5. **CPU inference on a loaded machine.** During this audit the user's other
   jobs kept about 6 CPUs busy. This machine has 12 logical CPUs (Windows
   reports 6 cores, 12 threads), so two CLIs at the default 8 threads each made
   about 22 busy threads on 12 CPUs. Parakeet v3 then took 11 s on a 10 s FLEURS
   clip (one clip took 199 s); on an idle machine it takes about 0.7 s. ggml
   synchronizes its threads with a spin barrier after every graph node, so a
   descheduled worker stalls the whole graph. This was observed, not
   benchmarked. The default thread count stays upstream's static one. A
   default that follows the machine's load would make transcripts depend on
   that load: ggml's CPU numerics are not thread-count invariant for every
   graph (Granite 4.0 1B wrote "semblait" at 8 threads and "semblerait" at 3
   on `fleurs-fr`, deterministically). A host that runs CPU inference next to
   other heavy jobs should pass an explicit `n_threads`.

8. **The CPU threadpool spins after each graph** (CPU sessions; the GPU case
   was item 18). The fork keeps one ggml pool
   per CPU backend with ggml's default hybrid polling (`poll = 50`): after a
   graph its workers busy-wait for some hundred milliseconds before they
   sleep. Only Parakeet parks the pool before its host-side decoder. In other
   families, a multithreaded host stage that starts right after a graph
   competes with the spinning workers. Measured on Granite 5 CTC, CPU, `dots`:
   mel 27.7 ms on a third back-to-back run vs 19.7 ms upstream (whose
   throwaway pool exits), 17.7 vs 23.2 ms on a first run, and no gap at 4
   threads. That is under 1% of the run, and it touches only back-to-back
   runs (`--batch`, streaming), not a single dictation. A fix would park the
   pool from each family before its host stages; parking centrally is unsafe
   while another session computes.
